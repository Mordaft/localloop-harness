Explicación Detallada de Nuestro Flujo Agéntico

La arquitectura agéntica de LocalLoop se sustenta en dos grafos orquestados mediante LangGraph.js dentro de una PWA desacoplada: el Grafo General de Agente (bucle reactivo ReAct continuo con delegación fractal) y el Grafo SDLC de Ciclo de Vida (fases formales de Descubrimiento, WBS/Plan, Arquitectura Gatekeeper, Construcción con Pruebas Sandbox, Auditoría E2E y Resiliencia RCA).

❖ Diagrama del Ciclo de Ejecución Agéntico (LLM Router ↔ Tool Runtime Loop)
1. Estado & Context Injection START
Inyección de AgentState (mensajes, skills activas, memorias episódicas recuperadas de engram-ts y presupuesto de turnos/tokens).
→
2. LLM Router Node Thinking & Choice
Inferencia con streaming SSE. El modelo razona internamente (bloque <think>) y decide: respuesta final o invocación de herramientas estructuradas.
→
3. Budget Edge Check Conditional Edge
Comprueba turnsUsed < maxTurns y presupuesto de tokens. Si se supera, desvía a halt_budget_exceeded y aborta de forma segura.
↓
6. Re-Inyección de Feedback Loop Back
Las salidas se incorporan como role: 'tool' asociado a tool_call_id. El grafo retorna a llm_router con el nuevo estado enriquecido.
←
5. Sanitización & Evidencias Observation Layer
Captura de logs, retorno JSON, aserciones y capturas visuales. Truncado de Base64 excesivo para proteger la ventana de contexto.
←
4. Tool Runtime Node Worker / Sandbox
Despacho asíncrono a FS Tools (File System Access API), Sandbox JS/DOM en iframe seguro, Engram Memory o servidores remotos MCP.

1.1. Cómo Ofrecemos las Herramientas al LLM

Las herramientas no se pasan como texto plano o prompts improvisados, sino mediante el estándar estricto OpenAI Tool Calling Specification tipado en JSON Schema. Esto permite que el LLM aproveche sus pesos entrenados para generación de llamadas a funciones nativas:

📁
Workspace FS Tools

fs_read_file, fs_write_file, fs_list_dir, fs_search. Operan directamente sobre el sistema de archivos local del usuario mediante la File System Access API interactiva con control de modificaciones por propuestas o escritura directa.

🧪
Sandboxes de Ejecución

run_sandboxed_js y run_browser_sandbox. Permiten ejecutar código JavaScript en un Web Worker o renderizar componentes HTML/CSS/DOM completos dentro de un iframe aislado con atributos sandbox restrictivos y captura de capturas visuales.

🧠
Memoria & MCP Externo

memory_search, memory_save, memory_get conectadas a engram-ts sobre IndexedDB. Además, conectores MCP vía SSE/WebSocket para consumir servidores y herramientas locales o en red sin tocar código.

Gating Dinámico de Herramientas: En el turno inicial de un trabajo, el sistema restringe las herramientas únicamente a lectura o planificación obligatoria (plan_and_delegate_tasks con toolChoice: 'required'). El LLM no tiene permitido escribir código en archivos sin haber formulado previamente una lista de tareas verificable donde cada tarea tenga definida su prueba de aceptación.
agent-graph.ts — Especificación Formal de Herramienta OpenAiToolSpec
export function getEngramToolSpecs(): OpenAiToolSpec[] { return [{ type: 'function', function: { name: 'plan_and_delegate_tasks', description: 'OBLIGATORIO: crea una lista de tareas donde cada elemento posee una prueba de aceptación (acceptanceTest) y se delega a un sub-agente independiente.', parameters: { type: 'object', properties: { workGoal: { type: 'string' }, tasks: { type: 'array', items: { properties: { id: { type: 'string' }, description: { type: 'string' }, acceptanceTest: { type: 'string', description: 'Prueba automatizada que valida la entrega' } }, required: ['id', 'description', 'acceptanceTest'] } } }, required: ['tasks'] } } }]; }

1.2. Qué Hace el LLM con las Herramientas

Durante la llamada de inferencia por streaming, el LLM lleva a cabo un proceso cognitivo trifásico estructurado:

  • 1. Razonamiento Explícito (CoT / Thinking Stream): Mediante el tag <think> emitido en tiempo real al callback onThinking, el modelo analiza el objetivo, compara el código existente con el estado deseado y delibera qué herramienta invocar.
  • 2. Planificación de Parámetros y Validación Sintáctica: El modelo serializa un objeto JSON estricto que encaja con el esquema de la función elegida. Si decide descomponer, formula las sub-tareas; si decide probar código, redacta el script de prueba y aserciones.
  • 3. Emisión de Tool Calls: En lugar de escribir código suelto en texto conversacional, emite un token de función estructurado con un identificador unívoco (tool_call_id: "call_abc123").

1.3. Cómo Usamos en el Proceso su Feedback (Observation Loop)

El bucle agéntico es estrictamente empírico: ninguna afirmación del LLM se da por buena sin contrastarla con el resultado del runtime de la herramienta. El proceso de feedback sigue este ciclo:

Captura & Sanitización Tratamiento del Resultado

El nodo ejecutor (toolRuntimeNode) intercepta la ejecución. Si la herramienta es fs_read_file, extrae el texto del archivo; si es run_browser_sandbox, captura logs del DOM, aserciones y capturas en base64. Para evitar sobrecargar la ventana de contexto del LLM, las imágenes base64 extensas se sanitizan como marcadores visuales y se persisten en IndexedDB.

Re-Inyección en el Grafo Alimentación del Siguiente Turno

El output resultante se empaqueta como un mensaje con rol role: 'tool' asociado a su tool_call_id correspondiente. Este mensaje se adjunta al array messages del AgentState. El borde cíclico de LangGraph devuelve el control a llm_router, haciendo que el modelo "vea" inmediatamente el resultado empírico de su acción.

1.4. Capacidad de Repetir una Tarea que No se ha Realizado Bien a la Primera

LocalLoop cuenta con tres niveles distintos de resiliencia y auto-corrección según la profundidad y naturaleza del error:

Nivel 1: Reintento Reflexivo Inmediato (Micro-Loop en ReAct) Turno a Turno
Si una llamada a herramienta falla (por ejemplo, fs_write_file sobre un directorio inexistente, error de sintaxis en run_sandboxed_js, o una aserción falsa lanzada en el sandbox), la excepción se captura en un bloque try...catch y se devuelve al LLM como un JSON de error: {"error": "TypeError: Cannot read properties of undefined"}.

El LLM procesa este mensaje en el siguiente turno del grafo, analiza en su bloque de pensamiento por qué falló la aserción o el compilador y emite una nueva llamada corregida. Este bucle puede repetirse hasta agotar el límite de turnos (por defecto 12 turnos) o el presupuesto de tokens (64,000 tokens).
Nivel 2: Verificación Atómica Obligatoria (runAndVerifyAtomicTest) Subagentes Hoja
Cuando un subagente fractal recibe una tarea, no se le permite reportarla como completada simplemente con una declaración de texto. El runtime ejecuta obligatoriamente la función runAndVerifyAtomicTest, que compila y ejecuta la prueba_automatizada en el sandbox seguro contra el criterio de prueba_aceptacion. Si la prueba falla, el entregable atómico no se certifica y los logs de aserción fallida quedan registrados en el sumario para obligar a una revisión antes de consolidar cambios.
Nivel 3: Bucle de Resiliencia y Análisis de Causa Raíz (Macro-Loop SDLC Fase 5 RCA) Arquitectura & Negocio
En el grafo SDLC formal (sdlc-graph.ts), tras completar todos los componentes unitarios, se entra en la Fase 4 de Auditoría E2E y Decisión de Negocio (un punto de interrupción con aprobación humana / HITL).

Si el evaluador o los tests E2E rechazan la entrega: el grafo no se detiene en un callejón sin salida. Se activa el nodo phase5_resilience:
  • Se instancia la skill especializada RootCause_Analyzer.
  • Se formula un diagnóstico formal de causa raíz (categorizado como BUSINESS_ASSUMPTION, TECHNICAL_DEBT, INTEGRATION_CONTRACT_MISMATCH, etc.).
  • Se emite una recomendación de remediación (remedyRecommendation) y se inserta una nueva historia de remediación en el Backlog.
  • Retorno del flujo: El borde del grafo conecta la Fase 5 de vuelta a la Fase 1 (Strategy and Plan), recalculando el plan WBS y el grafo de dependencias para re-ejecutar el ciclo con las nuevas especificaciones.
1.B

Flujo de Definición, Diseño Técnico con HITL y "Design by Contract"

Uno de los mayores desafíos de los sistemas agénticos es evitar que el agente de programación "adivine" la arquitectura o invente nombres de métodos sobre la marcha. En LocalLoop, el documento inicial de negocio y arquitectura no es un texto decorativo: es un modelo de datos estricto que atraviesa un proceso de refinamiento en 3 fases formales antes de que el subagente escriba una sola línea de código.

1. De Documento Markdown a Grafo de Estado Ejecutable (Fase 0: Los 3 Pasos)

El documento inicial donde se explica la necesidad de negocio y la visión de arquitectura de alto nivel se procesa en node_phase0_assess y node_phase0_process_discovery desglosándolo en tres estructuras tipadas dentro de Phase0ThreeStepData:

Paso 1: Negocio Casos de Uso & BDD

Captura el texto en lenguaje natural (rawBusinessLanguageText) y lo estructura en casos de uso con actores, Happy Path, flujos alternativos y criterios de aceptación en Gherkin (Given-When-Then) con impacto cuantificable.

Paso 2: Arquitectura As-Is, To-Be y Transición

Establece el estándar (marketArchStandard: Clean Architecture, C4, Hexagonal). Modela la Situación Actual (As-Is) y sus limitaciones, la Situación Deseada (To-Be) y, de forma crucial, la Situación de Transición (convivencia temporal con sistemas legados).

Paso 3: Solución Desglose de Componentes

Mapea la necesidad funcional a una lista de componentes técnicos (featureComponentMappings). Para cada uno define si se crea o evoluciona (CREATE | EVOLVE), su estado objetivo (DESIRED | TRANSITION) y sus dependencias Fin-Inicio (dependsOn).

¿Cómo influye este Markdown en la Planificación (Fase 1)?:
En node_phase1_strategy_and_plan, la lista de componentes se compila en un Grafo Acíclico Dirigido (DAG Fin-Inicio). Si el componente Servicio de Facturación depende del Motor Core, el servicio se marca automáticamente como status: 'BLOCKED' y el motor como status: 'READY'. El Component Scheduler despacha secuencialmente los componentes respetando el orden topológico: ningún subagente implementará un componente hasta que sus dependencias estén verificadas al 100%.

2. La Etapa de Diseño con Intervención Humana (Human-in-the-Loop)

Para garantizar que el software se ajuste exactamente a las tecnologías, librerías y estructuras deseadas por el usuario, el grafo incorpora puntos de interrupción forzados (interruptBefore de LangGraph):

❖ Puntos de Interrupción Humana (HITL) y Desglose Técnico en Fase 1 y 2
Pausa HITL 1 Fase 0
Validación de Descubrimiento: El sistema presenta el resumen de casos de uso y estándares antes de procesar el alcance.
→
Pausa HITL 2 (Crucial) phase1_confirm_framework
Acuerdo de Stack Tecnológico: El sistema propone framework, bundler, test runner y árbol de carpetas. Se detiene a esperar la confirmación o modificación del humano.
→
Fase 2: Diseño Técnico Contratos Tipados
Desglose de Métodos y Firmas: Para el componente activo, se definen interfaces TypeScript estrictas, DTOs y análisis de trade-offs.

En la Pausa HITL 2 (phase1_confirm_framework) ocurre la magia de la infraestructura:

  • El usuario puede indicar: "Queremos usar TypeScript estricto con TailwindCSS y Vite, separando la lógica en src/components/ y src/services/".
  • El nodo node_phase1_confirm_framework toma esa respuesta humana y materializa en el workspace los archivos fundamentales: package.json, tsconfig.json, y scripts ejecutables locales (setup.cmd para Windows y setup.sh para Unix).
  • A partir de ese instante, las rutas relativas de cada componente del DAG se recalculan para encajar con el árbol acordado.
sdlc-graph.ts — Ejemplo Real de Contratos de Interfaz Generados en Fase 2 TypeScript Interfaces & Methods
// Contrato formal generado por ComponentTechnical_Designer antes de la implementación: export interface InvoiceItem { description: string; unitPrice: number; quantity: number; } export interface InvoiceCalculationInput { items: InvoiceItem[]; taxRate: number; vatId: string; } export interface InvoiceCalculationResult { invoiceNumber: string; subtotal: number; taxAmount: number; total: number; isValid: boolean; generatedAt: string; } // Interfaz con métodos y firma que vincula a este componente con el resto del sistema: export interface IBillingCoreEngine { calculate(input: InvoiceCalculationInput): InvoiceCalculationResult; }

Inmediatamente después, el agente Gatekeeper de Arquitectura Empresarial (node_phase2_gatekeeper) audita este contrato. Si el componente es de transición (por ejemplo, un adaptador para sincronizar con un ERP legado), el Gatekeeper no lo rechaza pero genera formalmente una Ficha de Deuda Técnica (TechnicalDebtRecord) especificando el riesgo medio y el plan de desmantelamiento futuro, garantizando la trazabilidad.

3. Cómo Influye Esta Definición en el Sub-agente de Implementación ("Design by Contract")

Cuando el flujo llega finalmente a la Fase 3 (node_phase3_implement_component), el subagente encargado de escribir el código ya no es un agente "creativo" que deba inventar soluciones. Su prompt recibe un corsé técnico impenetrable:

🛡️ Lo que Recibe el Implementador en su Prompt
  • Marco Tecnológico Validado: state.frameworkConfig.framework (ej. React 18 / Vanilla TS).
  • Estructura de Directorios: state.frameworkConfig.projectStructureSummary.
  • Rutas Exactas: targetPath = "src/components/billing_core.ts".
  • Contratos Inmutables: La lista completa de esquemas e interfaces TypeScript aprobadas por el Gatekeeper en Fase 2.
  • Dependencias Resueltas: La lista de componentes que ya están en VERIFIED y cuyos métodos puede importar directamente.
🎯 Resultado en la Calidad del Código

El subagente solo tiene una misión: implementar las interfaces TypeScript respetando los tipos de entrada y salida, y guardarlas en la ruta prescrita (mediante fs_write_file o anotaciones path="...").

Se elimina de raíz la alucinación sobre librerías no deseadas, la creación de carpetas anárquicas o la incompatibilidad entre módulos, logrando una cohesión idéntica a la de un equipo humano con arquitectos senior y desarrolladores junior.

1.C

Especialización de Habilidades: Mapeo de Tareas a Visiones Diferentes

Uno de los mayores errores en los arneses agénticos es utilizar un único "System Prompt omnipotente" para todo el proceso. Un buen analista de negocio no piensa como un arquitecto empresarial, ni un arquitecto piensa como un programador de bajo nivel o un tester adversarial. LocalLoop resuelve esto mediante un Árbol Jerárquico de Skills y el despachador dinámico RuntimeSkillLoader.

En cada fase y en cada nodo del grafo, RuntimeSkillLoader.resolveContext(state) conmuta automáticamente tres dimensiones fundamentales del agente:

Fase del SDLC Skill / Rol Activo Visión y Sesgo Cognitivo Herramientas Permitidas
Fase 0 ProjectRigor_Interviewer Analista Funcional Enfocado en el valor para el usuario, lenguaje de negocio, casos extremos y criterios Gherkin (Given-When-Then). No piensa en código. ask_discovery_question save_use_cases
Fase 0 & 1 EnterpriseArch_MCP_Connector Arquitecto Empresarial Visión macro: compara el As-Is frente al To-Be, aplica estándares C4 y consulta el catálogo corporativo mediante servidores MCP remotos. mcp_connect_server engram_search
Fase 1 GovernanceProject_Planner Project Manager Técnico Planificación WBS y dependencias Fin-Inicio (DAG). Su obsesión es el orden topológico y que ningún módulo empiece sin sus cimientos. engram_search plan_and_delegate_tasks
Fase 2 ComponentTechnical_Designer Diseñador de Software Diseño de APIs limpias. Define interfaces TypeScript, métodos, firmas de tipos, dependencias entre módulos y análisis de pros/contras. engram_search propose_design_options
Fase 2 EnterpriseArch_Gatekeeper Auditor & Gatekeeper Juicio crítico de control. Si detecta soluciones de compromiso o adaptadores transicionales, exige documentar y tipificar la Deuda Técnica. approve_design register_technical_debt
Fase 3 Component_Implementer Desarrollador Coder Pragmático y riguroso. Su único objetivo es programar la clase o función que cumpla al 100% las interfaces de Fase 2 en las rutas definidas. fs_write_file fs_read_file
Fase 3 UnitTest_Engineer Ingeniero de QA / Testing Mentalidad de verificación empírica. Ejecuta el código en Sandbox JS o en Browser Iframe Sandbox; busca aserciones rotas y captura capturas visuales. run_sandboxed_js run_browser_sandbox
Fase 5 RootCause_Analyzer Especialista en Resiliencia Activado solo ante rechazo humano o fallo E2E. Investiga el motivo raíz (asunción de negocio errónea, limitación técnica) y reinyecta backlog en Fase 1. engram_search emit_rca_diagnosis
El Principio del Mínimo Privilegio de Herramientas (Tool Scoping):
Fíjate en cómo ComponentTechnical_Designer no tiene acceso a fs_write_file (no puede tocar el código fuente, solo propone interfaces en memoria Engram), mientras que Component_Implementer no tiene acceso a modificar el DAG ni a registrar deuda técnica. Esta separación hermética de herramientas es lo que impide que los agentes se desvíen de su responsabilidad específica.
1.D

Las Dos Dimensiones Fundacionales: MCP_CLI (La Maquinaria) y SKILLS (La Biblioteca de Referencia)

Un análisis crítico honesto de nuestra arquitectura revela dos vacíos estructurales que condicionan la capacidad real de fabricar software autónomo completo: la ausencia de maquinaria nativa de ejecución (MCP_CLI) y la carencia de una biblioteca de referencia con pautas precisas de actuación (SKILLS codificadas).

🧵 La Metáfora de la Fábrica Textil y la Cadena de Montaje de Software
📐 El Estado Actual: Dibujar Patrones en la Mesa de Corte

Nuestra PWA con File System Access API puede diseñar el patrón arquitectónico, definir interfaces y escribir código en los archivos del disco. Pero no tiene la maquinaria para coser, ensamblar ni planchar el traje. No sabe si el hilo resiste la tensión (compilación), si los botones encajan en los ojales (dependencias de paquetes) ni si el traje terminado le sienta bien al usuario (ejecución real en el host).

🏭 El Estado Objetivo: La Cadena de Montaje Completa (MCP_CLI + Referencias)

Para que el traje salga terminado de la fábrica necesitamos dos palancas que debieron concebirse desde el diseño original:
1. MCP_CLI: La maquinaria pesada que ejecuta pnpm install, tsc --noEmit, vite build y levanta el servidor real en el sistema operativo.
2. BIBLIOTECA DE SKILLS: Las muestras de tela, patrones maestros y manuales de corte (SOPs, Blueprints dorados y anti-patrones) que guían al sastre paso a paso.

Dimensión 1: `(MCP_CLI)` — El Entorno de Desarrollo como Maquinaria de Ejecución

Actualmente, el arnés de LocalLoop está confinado al navegador. Aunque el sandbox de Web Worker e Iframe es útil para pruebas sintéticas de DOM o lógica pura, está ciego ante el entorno nativo del host:

🔘 ¿Los Botones Escogidos?

El agente añade dependencias en el package.json (ej. lucide-react, zod, tailwind-merge). Pero como no puede invocar pnpm install o npm install, no sabemos si las versiones son compatibles, si existen en npm o si rompen la resolución de dependencias peer.

✂️ ¿El Corte y la Tela?

El agente escribe archivos TypeScript con rutas relativas (import { x } from './engine'). Sin invocar el compilador nativo tsc --noEmit, no podemos verificar si los tipos cuadran holísticamente en el proyecto o si hay errores de sintaxis que el sandbox aislado no llega a detectar.

👔 ¿El Traje Confeccionado?

Sin un puente al terminal del sistema, el agente no puede ejecutar vite build para ver si el bundle empaqueta limpio, ni puede arrancar el servidor de desarrollo en localhost:5173 para que el usuario o un subagente visual inspeccione la interfaz renderizada real.

La Solución Arquitectónica: Sidecar Local MCP_CLI (Protocolo Abierto):
Un servidor MCP local ultraligero corriendo en la máquina del usuario (vía SSE/WebSocket en http://localhost:3000/mcp) que expone 4 herramientas críticas a nuestro mcp-client.ts:
  • cli_exec_command: Ejecuta comandos reales del toolchain (pnpm install, tsc --noEmit, pnpm test, git status).
  • cli_dev_server: Inicia el proceso de desarrollo en segundo plano y reporta la URL local y los logs de compilación en caliente.
  • cli_git_snapshot: Crea commits transaccionales automáticos antes y después de cada turno de un subagente para permitir rollback instantáneo.
  • cli_env_diagnostics: Comprueba versiones de Node, memoria disponible y dependencias del sistema.

Dimensión 2: `(SKILLS)` — La Carencia de Biblioteca de Referencia y Pautas Precisas

Nuestros agentes tienen conocimientos generales procedentes del pre-entrenamiento de los LLMs. Pero el conocimiento paramétrico general es el enemigo de la consistencia técnica: el modelo "sabe mucho de todo", pero no sabe cómo lo hacemos exactamente en nuestro proyecto.

En nuestro código actual (skills-tree.ts), los prompts de los skills son instrucciones genéricas de una sola frase:
"[SKILL: Component_Implementer] Estás implementando el código del componente X. Escribe código modular, tipado y documentado..."
Al no suministrar pautas precisas de actuación ni ejemplos de referencia, el agente improvisa:

⚠️ Lo que Ocurre sin Biblioteca de Referencia
  • Alucinación de APIs Obsoletas: Usa patrones de versiones anteriores de librerías (ej. React router v5 en vez de v6, sintaxis obsoleta de Tailwind).
  • Anarquía Estilística: Un subagente usa clases con programación orientada a objetos, otro usa closures funcionales puras y otro crea singletons globales.
  • Inconsistencia en Testing: Cada subagente escribe los tests con aserciones diferentes, sin seguir un estándar de testing de la organización.
  • Falta de Restricciones Negativas: No sabe qué prácticas están terminantemente prohibidas en nuestro stack.
📚 Lo que Debe Ser una Skill Completa (Biblioteca Curada)
  • SOPs (Procedimientos Operativos Estándar):** Checklist obligatorio paso a paso que el agente debe verificar antes de dar por buena su entrega.
  • Ejemplos Dorados ("Golden Blueprints"): Snippets de código real del proyecto que sirven de plantilla "few-shot" del estándar esperado.
  • Catálogo de Anti-Patrones: Lista explícita de "Qué NO hacer jamás" (ej. prohibido usar any, prohibidos márgenes negativos, prohibido acoplar UI a IndexedDB).
  • Diccionario de Decisiones Tecnológicas: Si necesitas validación de formularios -> Zod; si necesitas iconos -> Heroicons; si necesitas testing -> Vitest.
skills/Component_Implementer.md — Estructura de Biblioteca de Referencia Estructura de Skill de Alto Rigor
# SKILL: Component_Implementer ## 1. Misión y Pautas Precisas de Actuación (SOP) 1. Lee los contratos tipados de Fase 2 antes de escribir una sola línea. 2. Cada archivo debe incluir cabecera con ruta: `// File: src/modules/...` 3. Prohibido estrictamente el uso del tipo `any`. Tipa parámetros y retornos. 4. Todo método asíncrono debe aceptar un `signal?: AbortSignal` opcional. ## 2. Conclusión Estratégica:
Si combinamos la maquinaria real de ejecución (MCP_CLI) para compilar y probar en caliente con una biblioteca de referencia viva (SKILLS con SOPs y Golden Blueprints), el agente deja de ser un generador de texto probabilístico y se transforma en un operador técnico cualificado integrado en una auténtica cadena de montaje industrial.

Análisis Crítico de Puntos Débiles de lo Planteado

A pesar de la sofisticación teórica de los grafos y la división en fases, un examen técnico riguroso de la implementación revela vulnerabilidades estructurales que pueden degradar la autonomía o inducir al fracaso en proyectos reales:

1. Autocomplacencia y Tautología en Pruebas Sintéticas
Crítico
En la función procesarNodoScope, el mismo subagente que genera el código (tarea_realizada) es el que redacta la prueba automatizada (prueba_automatizada). Si el LLM tiene una concepción errónea de la regla de negocio, redactará un test que valide su propio error o escribirá aserciones triviales tipo return true; o verificaciones puramente superficiales que siempre pasan en el sandbox sin probar casos esquina ni resistencia a fallos.
Impacto Sistémico: Falso positivo continuo: el sistema reporta 100% de tests unitarios superados (PASS), pero el código final no satisface la necesidad real de la aplicación.
2. Efecto "Groundhog Day" y Atrapamiento en Mínimos Locales
Alto
Cuando un modelo mediano o local (ej. 7B u 8B en Ollama/LM Studio) comete un error en la sintaxis de una herramienta o falla una aserción, su respuesta típica al ver el error del sistema no es cambiar de paradigma algorítmico, sino repetir exactamente la misma llamada con variaciones cosméticas (modificando espacios o saltos de línea). Esto consume los turnos disponibles (turnsUsed) hasta llegar al corte abrupto por halt_budget_exceeded sin haber progresado.
Impacto Sistémico: Agotamiento improductivo del presupuesto de turnos y tokens con sesiones bloqueadas a mitad del desarrollo.
3. Falta de Transaccionalidad y Rollback en Modificaciones del Workspace
Alto
La herramienta fs_write_file escribe directamente en los ficheros del disco del usuario a través de la File System Access API. Si un agente modifica 3 archivos de un componente y falla al compilar en el cuarto o se detiene por budget, los cambios ya están grabados en disco de forma irreversible. No existe un mecanismo de "staging" o rollback automático con Git que devuelva el repositorio al commit limpio anterior ante un fallo del agente.
Impacto Sistémico: Workspace en estado incoherente, código roto a mitad de refactorización y necesidad de intervención manual del desarrollador para limpiar el diff.
4. Degradación de Atención por Crecimiento de Contexto (Lost in the Middle)
Medio-Alto
Conforme el agente realiza llamadas a fs_read_file, inspecciona el árbol de ficheros y recibe trazas de sandbox, el historial de state.messages se infla rápidamente a decenas de miles de tokens. Los LLMs sufren pérdida de fidelidad en la atención para tokens situados en la zona intermedia de la ventana, lo que hace que el agente "olvide" las restricciones arquitectónicas iniciales o las directrices del System Prompt suplementado.
Impacto Sistémico: Desviación arquitectónica progresiva en sprints de más de 6-8 turnos continuos.
5. Latencia Crítica en Modelos Locales Cuantizados (SLM en PWA)
Medio
Ejecutar la descomposición fractal completa (donde un nodo raíz lanza 3 subagentes, cada uno de los cuales lee ficheros, ejecuta tests en worker y compila entregables) exige entre 15 y 25 llamadas secuenciales o semi-concurrentes al LLM. Si el usuario está usando una GPU local de consumo con un modelo como Qwen 2.5 Coder 7B o Llama 3.1 8B a 25-35 tokens/s, el ciclo completo de un solo componente puede tardar entre 4 y 8 minutos, comprometiendo la interactividad.
Impacto Sistémico: Experiencia de usuario pesada que desincentiva los bucles de auto-corrección profunda si se ejecutan 100% en local.
6. Aislamiento Asimétrico del Sandbox Browser vs Entorno Node/NPM Real
Medio
El sandbox de LocalLoop corre en el navegador (Web Worker para JS puro o iframe para DOM/CSS). Aunque es excelente para componentes visuales y utilidades Vanilla TypeScript, no puede ejecutar binarios nativos del sistema (como pnpm build, tsc --noEmit, linters CLI de ESLint o servidores Docker) sin un puente MCP externo. Por tanto, el agente no valida si el proyecto compila holísticamente en el toolchain del sistema operativo.
Impacto Sistémico: El código pasa los tests aislados del sandbox pero rompe el build global de Vite o TypeScript al ejecutar en consola.

Conclusiones: Posibilidades de Éxito de un Proyecto de Forma Correcta

La tasa de éxito no es un valor binario absoluto; depende directamente de la complejidad dimensional del software, de la calidad del oráculo de verificación y del tamaño de la ventana de acoplamiento entre módulos. A continuación se presenta la evaluación probabilística basada en la arquitectura actual:

Nivel 1: Scaffolding, Micro-componentes y Funciones Aisladas
Generación de algoritmos, transformadores de datos, componentes UI puros, utilidades regex, endpoints CRUD.
90%
Nivel 2: Módulos con Dependencias Locales y PWA Autocontenida
Juegos Web (Tetris, Canvas), paneles interactivos, clientes API con tipado TypeScript estricto, stores IndexedDB.
75%
Nivel 3: Refactorización de Código Existente en Repositorios Medios
Modificación de contratos entre múltiples ficheros existentes, migración de dependencias, adaptadores legados.
50%
Nivel 4: Proyectos Full-Stack de Gran Escala o Sistemas Distribuidos
Monorepos con decenas de paquetes, microservicios interdependientes, concurrencia asíncrona compleja.
25%
✓ Factores que Garantizan el Éxito

1. Descomposición por Pruebas de Aceptación: La regla que impone definir la prueba antes que el código es el mayor acierto del diseño; reduce la dispersión del LLM al forzar un objetivo cerrado.

2. Interrupciones Human-in-the-Loop (HITL): Los 3 puntos de pausa en Fase 0, Fase 1 y Fase 4 evitan que el modelo se gaste cientos de miles de tokens persiguiendo un objetivo de negocio mal interpretado.

✕ La Barrera del "Último 10%"

En ingeniería de software con agentes, el primer 80-90% del código se genera con facilidad y alta elegancia. El fracaso ocurre casi siempre en el 10% final: detalles de tipado estricto, gestión de rutas relativas, colisiones de nombres o casos frontera que el agente no es capaz de resolver sin un oráculo de compilación determinista real.
